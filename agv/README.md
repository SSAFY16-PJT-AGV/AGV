# agv/ — JETANK 탐색 주행

로봇이 바닥 라인을 따라 돌면서 색 패치와 갈림길(갈라짐·합쳐짐)을 검출해 이벤트 로그로 남기고, 안 가 본 가지를 골라 매트 전체를 탐색한다. 맵은 그 로그로 `mapping/build_map.py`가 만든다. 완성된 맵이 있으면 목표 패치까지 찾아가 멈추거나, 스퍼 끝에 들어가 주차한다([goto](#완성된-맵에서-목표로-가기-goto)).

지금 실제 매트(2m × 1m)에 쓰는 맵은 탐색 대신 매트 도안으로 만든 `maps/mat_ssafy_v3.json`이다(2026-11-25 새 배치, 노드 이름은 트윈 ID N01~N08·J·D. 예전 배치는 `mat_ssafy_v2.json`)(`mapping/design_map.py`, [mapping/README.md](../mapping/README.md)). 탐색으로 맵 만들기는 뒤로 미뤘고, 아래 현장 순서의 1~3번(카메라 자세, 색, 속도 보정)은 맵을 보고 주행할 때도 그대로 필요하다.

Jetson Nano 기본 이미지(Python 3.6, OpenCV, jetbot)에서 돌아가며, 추가 설치는 필요 없다. 서버 주문으로 움직이는 `serve` 모드만 MQTT 라이브러리가 필요하다(`pip3 install --user "paho-mqtt<2"`, [아래](#서버-주문으로-움직이기-serve)).

## 구성

| 파일 | 내용 |
| --- | --- |
| `explore.py` | 실행 진입점. 카메라 → 인식 → 이벤트 기록 → 모터 |
| `runner.py` | 한 프레임 처리 로직. 시뮬레이터(`sim/mat/`)도 같은 코드를 쓴다 |
| `linecam.py` | 라인·색 패치·갈림길 검출, 라인 추종 조향 |
| `topo/` | 이벤트 로그 형식, 탐색 정책(안 가 본 가지 우선), 맵 빌더, 주행 기록으로 맵 모양 계산(`shape.py`) |
| `nav/` | 완성된 맵 위 이동: 맵 읽기(`navmap.py`), 이벤트로 위치 추적·갈림길 선택·정지(`navigator.py`) |
| `link/` | 서버 연동(MQTT): 주문 검사(`orders.py`), 주행과 잇기(`controller.py`), 맵 위 자세(`geometry.py`), rear_clear 자원(`segments.py`), 연결(`mqtt.py`) |
| `hw.py`, `motordrv.py` | 카메라(GStreamer / jetbot / 녹화 영상), 모터(jetbot Robot, 없으면 모터 보드 PCA9685를 I2C로 바로) |
| `arm.py` | 카메라 자세(팔 서보 1·2·3·5번 각도) 읽기·맞추기·저장. 저장한 자세는 시작할 때 자동으로 맞춤 |
| `tools/camtool.py` | 현장 보정: 카메라 자세 맞추기·저장(`arm`), 화면 저장(체커보드 확인 포함), 바닥 좌표계용 회전 사진, HSV 측정, 속도 측정 |
| `camcalib.py`, `tools/calib.py` | 체커보드 사진으로 렌즈 보정값(어안/핀홀 자동 선택) 계산·불러오기 |
| `speedcal.py` | 색 패치를 지날 때마다 실제 주행 속도를 다시 재서 이동거리 보정 |
| `tools/autocolor.py` | 한 바퀴 영상에서 패치 색 범위·문턱 자동 보정 |
| `tools/runlog.py` | 주행 결과(events.jsonl) 요약: 타임라인, 막다른 길·V자 값, 종료 이유 |
| `perception/` | 선반 집기·적재 인식([설계](../docs/perception/shelf-perception.md)): ArUco 검출 직접 구현(`aruco.py`, cv2.aruco 없이), 렌즈·카메라 위치(`camera.py`), 칸 판정(`shelf.py`의 `perceive_shelf`), 가상 선반 장면(`scene.py`) |
| `task/` | 선반 작업(집기·놓기·보기): 할 일 정하기(`decide.py`), 관측 자세 → 칸 보기 → 팔 → 다시 보기 → 주행 자세를 프레임마다 진행(`executor.py`), 팔 인터페이스(`arm_driver.py`). 서버 메시지 변환은 `link/task_msgs.py` 한 곳([형식](../docs/protocol/shelf-task.md)) |
| `tools/markers.py` | 선반 띠(칸 마커 4개, 칸 간격 그대로)·물건 마커 인쇄 파일(PDF/PNG, 300dpi, 100mm 눈금) |
| `tools/shelfcheck.py` | 선반 앞에 세워 두고 칸 인식만 확인(주행·서버 없이): 칸 상태, 선반 위치(줄자와 비교), 밝기, 판정 시간, 관측 자세 찾기(`--sweep --save-observe`). 현장 순서는 FIELD_TEST.md 10절 |
| `tools/shelfsim.py` | 가상 선반 장면 여러 장으로 칸 판정 정확도 측정(정차 오차·카메라 보정 오차를 넣어 볼 수 있음) |
| `config/explore.json` | 두 대 공통 값. `linecam.DEFAULT_CONFIG`를 덮어쓴다 |
| `config/perception.json` | 선반 인식 기본값(렌즈, 카메라 위치, 팔 범위, 마커, 박스, 선반). 항목마다 근거(`_src`), 추정값은 실측해서 고침 |
| `config/robots/<ID>/` | 로봇마다 잰 값(`explore.json`: 카메라 자세·색·판정 지점·trim, `camera_calib.json`: 렌즈 보정값). 공통 값을 덮어쓴다. 로봇 ID는 `tools/robotcfg.py init`(`robotcfg.py`) |

## 현장 순서

**로봇 ID 먼저(젯슨마다 한 번)**: `python3 -m agv.tools.robotcfg init physical-1`(2호기는 `physical-2`). 아래에서 저장하는 현장 값은 모두 그 로봇 폴더(`config/robots/<ID>/`)로 간다. 예전에 공통 파일에 저장해 둔 젯슨은 `init physical-1 --move-local`로 옮긴다([FIELD_TEST.md](FIELD_TEST.md) 0단계).

막다른 길·V자까지 단계별로 시험하는 체크리스트는 [FIELD_TEST.md](FIELD_TEST.md)에 있다. 주행 결과 요약은 `python3 -m agv.tools.runlog data/runs/<시각>`으로 본다.

저장소 루트에서 실행한다. 주피터 노트북이 카메라를 잡고 있으면 먼저 그 커널을 끈다.

1. **카메라 자세 정하기(처음 한 번)**: `python3 -m agv.tools.camtool arm --view`
   - Waveshare 서보 라이브러리 `SCSCtrl`이 필요하다. 없다고 나오면 `cd ~ && git clone https://github.com/waveshare/JETANK.git && cd JETANK && pip3 install --user .`(받아만 둬도 `~/JETANK`에서 찾아 씀). 포트 권한·시리얼 콘솔 문제는 [FIELD_TEST.md](FIELD_TEST.md) 0단계.
   - 로봇을 라인 위에 놓고 브라우저(`http://<젯슨 IP>:8080`)로 검출 화면을 보며 키보드로 맞춘다. `1`·`2`·`3`·`5`로 서보(팔 좌우, 팔 아래 관절, 팔 가운데 관절, 카메라 상하)를 고르고 `+`/`-`로 움직인다(`[` 1도씩, `]` 5도씩). 손으로 맞추려면 `f`로 힘을 뺐다가 `f`로 고정한다. `p`로 저장, `q`로 끝.
   - 라인이 화면 아래 절반의 가운데쯤 보이고, 가로줄마다 초록 점이 하나씩 찍히면 된다. 상태 표에 "선 하나로 보이는 줄", "조향 줄 선 위치"가 숫자로 나온다. `--view`가 없으면 `data/snap/arm_preview.png`를 계속 저장한다.
   - 저장한 각도(로봇 설정 `config/robots/<ID>/explore.json`의 `arm.servo_angles`)는 이후 `explore`, `camtool snap`/`ground`, `autocolor --camera`가 시작할 때 자동으로 맞춘다. 맞춘 뒤 다시 읽어 3도 넘게 다르면 경고한다. 팔을 건드리지 않으려면 `--no-arm`. `camtool arm --read`는 지금·저장한 각도 출력, `--apply`는 맞추기만, `--save-now`는 지금 자세를 그대로 저장.
   - 자세를 다시 저장하면 그 자세에서 잰 값(5번 판정 지점 거리, 7번 렌즈 보정·바닥 사진)을 다시 잰다. 저장할 때 목록이 나온다.
   - 확인: `python3 -m agv.tools.camtool snap` → `data/snap/debug.png`. `full.png`(원본 해상도)도 같이 저장된다. 검출 그림과 HSV 측정은 주행 해상도인 `raw.png` 기준이다.
   - GStreamer가 안 열리면 `--camera jetbot`으로 바꾼다(이때는 노출 고정이 안 됨). JetPack이 오래돼 `aelock`을 모르면 `camera.lock_exposure`를 `false`로 둔다.
2. **색 자동으로 잡기**: 맵을 한 바퀴 도는 영상에서 패치 색 범위를 자동으로 잡는다. 라인 추종은 검은 선만 보므로 색이 안 맞아도 로봇이 직접 돌 수 있다.
   - `python3 -m agv.explore --mode lap --enable-motors --record --view`로 한 바퀴 돈다. 매트에 시계 방향으로 놓으면 갈림길마다 왼쪽(바깥 큰 고리)으로 가고 V자는 들어가지 않아 모든 패치를 한 번씩 지난다. 갈라짐·합류·교차의 순서와 간격이 되풀이되는 것을 보고 한 바퀴를 알아본 뒤 스스로 멈춘다(못 알아보면 240초). 반시계 방향이면 `--lap-side right`. 이 주행의 패치 검출은 틀려도 상관없고 영상만 있으면 된다.
   - `lap`이 엉뚱한 쪽으로 가면 `--mode ask`로 갈림길을 직접 고른다(고를 쪽은 `FIELD_TEST.md` 2단계). 모터가 준비되지 않았거나 선을 못 따라가면 `--mode passive`로 로봇을 손으로 밀어 한 바퀴 녹화한다.
   - 처음 바퀴를 굴리기 전에 앞으로 가는지 확인한다. 바퀴 방향이 반대면 `robot.invert_left/right`를 고친다.
   - `python3 -m agv.tools.autocolor data/runs/<시각>` → 색마다 새 H 범위, 바꿀 문턱, **그 영상에서 잡히는 패치 순서(기존 설정 vs 새 설정)**가 나온다. `autocolor.png`에서 이름표와 실제 패치 사진이 맞는지 본다.
   - 괜찮으면 `--write`를 붙여 다시 실행한다. 로봇 설정(`config/robots/<ID>/explore.json`, 로봇 ID가 없으면 `config/explore.json`)에 쓰고 원래 파일은 `.bak-<시각>`으로 남는다. 라인 문턱(`line.v_max` 등)은 지금 값이 안전한 범위면 그대로 둔다.
   - 조명이 바뀌면(낮/밤, 다른 강의실) 한 바퀴 다시 찍어 돌리면 된다. 녹화 없이 `--camera gst --seconds 60`으로 카메라에서 바로 찍을 수도 있다.
   - 이름은 무지개 순서(빨강→주황→노랑→초록→파랑→보라)로 붙인다. 매트에 일부 색만 있으면 `--colors red,blue,...`로 알려 준다. 바닥·신발 같은 다른 색이 잡히면 화면에 안 들어오게 다시 찍는다.
   - 손으로 재야 할 때: `snap` 후 `python3 -m agv.tools.camtool hsv data/snap/raw.png x y w h`.
3. **검출 확인**: 보정한 색으로 한 바퀴 더 돈다(`--mode lap --enable-motors --record`, 모터 없이 보려면 `--mode passive`로 손으로 밀기). 색을 잡은 뒤(`autocolor --write`)에는 `lap` 모드도 패치 속도 보정을 켠다(`--speedcal on/off`로 바꿀 수 있음).
   - 터미널에 `patch`(맵의 색 전부), `split`, `merge` 이벤트가 찍혀야 한다.
   - 결과 폴더의 `debug/*.jpg`에서 검출 상태를, `camera.mp4`로는 노트북에서 다시 돌려 볼 수 있다: `python3 -m agv.explore --camera video:<폴더>/camera.mp4`
4. **패치 길이 재기**: 색 패치의 진행 방향 길이를 자로 한 번 재서 `patch.length_mm`에 넣는다. 길이가 다른 패치는 색별로 `patch.length_mm_by_color`에 넣는다(새 매트 충전 패치 분홍·하늘은 공통 설정에 149mm로 들어 있음, 실물로 다시 잴 것). 그러면 주행 중 패치를 지날 때마다 실제 속도를 다시 재서 이동거리를 보정한다. 배터리가 닳아 느려지거나 바닥이 바뀌어도 따라간다. `robot.speed_mm_s`는 첫 패치를 지나기 전까지만 쓰는 짐작값이라 기본값(150)으로 둬도 된다. 바퀴 방향이 반대면 `robot.invert_left/right`를 고친다.
   - 패치 길이를 못 쓰는 맵이면 예전처럼 `python3 -m agv.tools.camtool speed --enable-motors`로 속도를 재서 `robot.speed_mm_s`에 넣는다.
5. **판정 지점 거리 재기**: `snap`의 `debug.png`에서 파란 가로줄이 바닥 어디에 해당하는지 자로 재서 `geom.ctrl_ahead_mm`에 넣는다(차체 궤도 가운데 기준).
6. **갈림길만 사람이 고르는 주행**: `python3 -m agv.explore --mode ask --enable-motors`
   - 갈라지는 곳에서 멈추고 왼쪽/오른쪽을 묻는다. 라인 추종이 흔들리면 `follow.base_speed`를 낮추고 `follow.kp`를 조정한다.
7. **렌즈 보정(카메라 캘리브레이션)**: 지금 주행과 맵 생성에는 안 쓴다. 다음 단계(카메라와 패치로 바닥 mm 좌표를 재서 맵 모양을 더 정확하게)에 필요하니 현장에 간 김에 찍어 둔다. 계산은 노트북에서 해도 된다.
   - 주행 자세(팔 각도) 그대로 `python3 -m agv.tools.camtool snap --count 25 --out data/calib`. 1.5초마다 한 장씩 찍으며 장마다 체커보드가 보였는지(O/x) 알려 준다. 보드를 화면 가운데·네 귀퉁이·가장자리로, 30~45도 기울여 가며 옮긴다.
   - `python3 -m agv.tools.calib data/calib` → 일반(핀홀)·어안 모델을 둘 다 계산해 재투영 오차가 작은 쪽을 고른다. 오차 1px 아래, 화면 덮은 비율 60% 이상이면 좋다. `calib_check.png` 오른쪽(편 사진)에서 곧은 선이 곧게 보이는지 확인하고 `--write`로 `config/robots/<ID>/camera_calib.json`에 저장한다.
   - 보정값은 그 센서 모드에서만 맞는다. `camera.capture_width/height`나 `flip`을 바꾸거나 초점 링을 돌리면 다시 찍는다(주행 시작 때 안 맞으면 경고).
   - 설계 문서 5.2절은 ChArUco 보드를 쓰지만, Jetson 기본 OpenCV(4.1.1)에는 aruco 모듈이 없을 수 있어 일반 체커보드를 쓴다. 렌즈 보정값은 같게 나온다. 보드 크기(안쪽 모서리 9x6 등)는 자동으로 찾고, 칸 크기는 결과에 영향이 없다.
   - 같이 찍어 둘 것: 로봇을 라인 위, 패치가 앞 15~25cm에 통째로 보이게 세우고 `python3 -m agv.tools.camtool ground --enable-motors --out data/ground` (제자리에서 좌우로 조금씩 돌며 9장).
8. **자율 탐색**: `python3 -m agv.explore --mode drive --enable-motors --record`
   - 갈림길마다 안 가 본 쪽을 고르고, 모든 가지를 다 돈 뒤 같은 패치로 한 바퀴 깨끗하게 돌아오면 그 패치에서 멈춘다(`end` 이벤트의 `reason`이 `explore_explored`).
9. **맵 만들기**: `python3 mapping/build_map.py data/runs/<시각>/events.jsonl -o maps/<이름>.json` → `mapping/viewer/index.html`에 끌어다 놓는다.
   - 같은 폴더의 `trace.jsonl`로 로봇이 실제로 지나간 궤적을 되살려 노드 좌표와 엣지 곡선을 계산한다(렌즈 보정 불필요). 터미널의 `모양 계산` 줄에서 같은 노드 방문 위치 차이가 작은지 본다. 자세한 내용과 트윈으로 보내는 `--twin`은 [mapping/README.md](../mapping/README.md).

**실시간 화면**: 어느 모드든 `--view`를 붙이면 로봇이 웹 서버를 띄운다. 터미널에 나온 주소(`http://<젯슨 IP>:8080`)를 같은 와이파이의 노트북·폰 브라우저로 연다. 검출 그림, 주행 상태(라인 추종/후진/회전), 최근 이벤트, **정지 버튼**이 나온다. 와이파이가 기기끼리 통신을 막으면 SSH로 포트를 넘겨 `ssh -L 8080:localhost:8080 <사용자>@<젯슨 IP>` 후 `http://localhost:8080`로 연다. 보는 사람이 없으면 그림을 만들지 않아 주행에 영향이 없다. 모니터가 연결돼 있으면 `--show`로 OpenCV 창을 띄울 수도 있지만, `ssh -X`로 원격 창을 띄우면 느려서 `--view`를 권한다. 녹화 영상 재생(`--camera video:...`)에 `--view`를 붙이면 실제 속도로 재생된다.

Ctrl+C를 누르면 모터를 세우고 `end` 이벤트를 남긴 뒤 끝난다. ask·drive 모드는 `--enable-motors` 없이는 실행되지 않는다.

## 완성된 맵에서 목표로 가기 (goto)

```
# 주황 패치 조금 앞에 시계 방향으로 놓고, 초록 패치 가운데에서 멈추기
python3 -m agv.explore --mode goto --map maps/mat_ssafy_v3.json --start N01 --to N05 --enable-motors --record --view

# 빨강 스퍼 끝에 주차 -> 3초 뒤 후진해 나와 파랑 패치로(--then은 쉼표로 여러 개, --wait 초)
python3 -m agv.explore --mode goto --map maps/mat_ssafy_v3.json --start N01 --to D03 --then N02 --enable-motors

# 정해진 경로 따라가기(서버 주문의 nodes와 같은 뜻). 첫 노드 조금 앞에 놓는다
python3 -m agv.explore --mode goto --map maps/mat_ssafy_v3.json --route N01,J02,J07,N03 --enable-motors

# 모터 없이 위치 추적만 확인(손으로 밀거나 녹화 영상 재생)
python3 -m agv.explore --mode passive --map maps/field_v2.json --record
python3 -m agv.explore --camera video:data/runs/<시각>/camera.mp4 --map maps/field_v2.json
python3 -m agv.tools.runlog data/runs/<시각>      # "이동(goto)" 칸에 갈림길 판단·도착 판정
```

탐색과 같은 라인 추종·갈림길 판정·V자 들어가기·막다른 길 되돌아 나오기 코드를 그대로 쓰고, 갈림길에서 갈 쪽을 고르는 부분만 탐색 정책 대신 `nav.Navigator`가 정한다.

- **위치 추적**: 맵 위에서 "지금 어느 엣지를 달리는지" 후보(가설)를 들고 다니다가, 이벤트(패치·갈라짐·합쳐짐·교차·스퍼)가 올 때마다 맵과 맞춰 본다. 합류·교차·갈림길 검출을 한 번 놓치거나 맵에 없는 합류·스퍼가 보여도 비용을 매겨 견딘다. 맵상 있을 수 없는 패치가 보이면 그 패치에서 다시 위치를 잡는다(패치 색은 맵에 하나씩).
- **시작 위치**: `--start`는 처음 보게 될 노드다(보통 출발 패치). 안 주면 처음 보이는 패치에서 위치를 잡는다. 그 전에 갈림길을 만나면 기본(왼쪽)으로 간다.
- **갈림길**: 갈래마다 목표까지 남은 거리(맵 엣지 길이)를 비교한다. 갈라지는 모습이 패치 스퍼나 스퍼 갈림(T 노드) 자리에서 보이면 스퍼로 보고 반대쪽으로 지나간다(되돌아 나오기 없이).
- **멈추는 자리**: 목표 패치의 앞 가장자리를 본 뒤 `patch.length_mm`의 절반(없으면 80mm, `--stop-offset`)만큼 더 가서 선다. 차체 가운데가 패치 가운데쯤 온다. 합류 바로 뒤 패치는 교차 판정 때문에 기록이 늦게 나지만, 정지 위치는 패치를 본 순간 정한다.
- **스퍼 끝(`D_<노드>`)에 주차**: 스퍼가 갈라지는 부모 노드(패치·스퍼 갈림 T)까지 가는 길을 고른다. 부모 패치를 지난 뒤 스퍼가 옆으로 뻗은 모습(`tee`)이 보이면, 차체 가운데가 갈림 지점에 올 때까지 가서 스퍼 쪽으로 제자리 회전해 스퍼를 탄다(V자와 같은 동작). 스퍼가 갈림길로 보이면 그 가지를 그대로 탄다. 선 끝이 보이면 되돌아 나오는 대신 차체 가운데가 선 끝에서 `recover.park_back_mm`(20mm) 앞에 올 때까지 더 가서 선다. 다음 목표를 받으면 후진으로 갈림 지점까지 돌아와 반대쪽으로 회전해 본선을 탄다(막다른 길 되돌아 나오기와 같은 동작). 스퍼 안에서 본 이벤트는 위치 추적에 쓰지 않는다.
- **스퍼를 못 봤을 때**: 부모 패치를 지나 26cm 안에 스퍼가 안 보이면, `--to`(최단 경로)는 한 바퀴 돌아 2번까지 다시 해 보고, 정해진 경로(`--route`, 서버 주문)는 예약 밖으로 돌 수 없으니 그 자리에서 선다(`nav_spur_missed`).
- **양방향과 유턴**: 맵 엣지가 `bidirectional: true`(build_map 기본)면 반대 방향으로도 다닌다. 반대로 지나면 갈림길은 합류로, 합류는 갈림길로 보이고(가지는 맵 합류 노드의 `inputs`를 좌우 뒤집은 것), 패치 스퍼는 오른쪽에 있다. 방향을 바꾸는 건 `uturn` 노드에서만이다. 패치 가운데에서 스퍼 반대쪽으로 180도 돌거나(선이 화면에서 다 사라지는 순간을 거친 뒤 뒤쪽 선을 잡음), 스퍼 끝에서 후진해 나와 스퍼 쪽으로 90도 돈다(이어 가려면 스퍼 반대쪽). 경로 비용에 유턴 한 번은 500mm로 잡는다. 반대 방향으로 놓고 출발하면 `--reverse`. 한쪽 방향 맵(`build_map --one-way`, 예전 `directed`)이면 탐색한 방향으로만 다닌다. 경로(주문)가 갈림길·합류 같은 유턴 못 하는 노드에서 되돌아가면 거절한다.
- **경로·대기(서버 연동 준비)**: `Navigator.set_route(nodes, release)`는 주문의 `nodes`·`released_until`과 같은 뜻이다. 같은 노드를 두 번 지나는 경로(되돌아오기)도 어디까지 왔는지 세며 따라간다. 해제 노드가 끝이 아니면 그 자리에서 대기(`hold`)하고, `extend(새 해제 노드)` 후 `runner.resume()`으로 이어 간다. 해제 노드가 갈림길이면 갈림길에 들어가기 전에 선다. 경로 밖 엣지로 들어선 것이 확실하면 바로 선다(`nav_off_route`). 혼자 도는 `goto` 모드에서는 대기를 풀 서버가 없어서 대기하면 끝낸다.
- **못 찾을 때**: 목표를 정한 뒤 패치를 (패치 수 × 3 + 2)번 지나도 못 가면 선다(`nav_gave_up`).
- **종료 이유**: `nav_arrived`(도착), `nav_off_route`, `nav_gave_up`, `line_lost` 등. goto는 도착하면 종료 코드 0이다.

알아 둘 것:

- **목표는 패치(새 맵 `N01`~`N08`, 탐색 맵 `P_<색>`)나 스퍼 끝(`D01`~`D08`, 탐색 맵 `D_P_<색>`)으로 정한다.** 탐색 맵의 갈림길 번호(`S1`, `M2`)는 맵을 다시 만들면 바뀔 수 있다. 경로(`--route`, 주문)는 스퍼 끝으로 끝나거나(`..., N03, D03`) 스퍼 끝에서 시작해도 된다(`D03, N03, ...`).
- **스퍼 길이와 비켜 서기**: 주차하면 차체 가운데가 본선에서 (스퍼 길이 - 2cm)쯤 떨어진다. 다른 로봇이 지나가려면 이 거리가 (차체 길이의 절반 + 지나가는 로봇 폭의 절반 + 여유)보다 커야 한다. 지금 도안의 스퍼(약 16~19cm)는 이보다 짧을 수 있으니 실제 차체로 재 보고 필요하면 스퍼를 늘린다.
- **스퍼를 못 보는 자리**: 패치 위 X자 교차와 겹친 스퍼(예전 도안의 노랑)는 교차로 보여서 들어가지 못한다. 모서리를 막 돌았거나(새 매트 N01, 모서리 끝에서 17cm) 흔들리며 패치에 들어오면 스퍼가 비스듬히 보인다. 예전 검출은 이때 확인 프레임이 끊겨 자주 놓쳤고(시뮬레이션 N01 10번 중 6~8번), 지금은 느슨한 기준으로 확인을 이어 센다(아래 검출 방식). 그래도 놓치면 goto는 한 바퀴 돌아 다시 들어가고, 서버 주문(경로 모드)은 `nav_spur_missed`로 선다. 곡선에서 합류한 직후의 스퍼(도안의 빨강)는 비스듬히 들어가 2cm쯤 옆으로 비켜 선다.
- **유턴 직후 바로 앞 갈림길**: 유턴이나 스퍼 탈출 회전을 마친 자리에서 20cm 안에 갈림길이 있으면 갈라지는 모습이 이미 화면에 있어 갈림길 판정이 안 된다. 그래서 회전 직후 탈 가지를 미리 고른 채로 따라간다(도안의 빨강 스퍼에서 되돌아 나와 M3, 보라에서 유턴해 M1). 실기체에서 꼭 확인할 자리다.
- 맵은 지금 탐색기 출력(agv-map-v1, m 단위)과 통일 제안 형식(`docs/mapping/map-schema.md`: mm, `pos`/`shape`, `bidirectional`, 중간 노드 `V_*`)을 둘 다 읽는다.
- **패치에 겹친 합류점(새 맵 J03·J07)**: 안쪽 세로선이 보라(N04)·빨강(N03) 패치 위에서 바깥 선에 붙어, 합류 판정이 패치에 묻힌다. 위치 추적은 패치로 바로잡아 문제없다. 서버가 해제 노드(`released_until`)를 J03·J07로 주면 그 바로 뒤 패치에서 서고, 서버에는 그 합류점에 섰다고 보낸다(`stopped_at: J07`, 두 자리는 사실상 같은 곳). 상태의 `last_node`는 패치(N03)로 나온다. 예전에는 패치를 보는 순간 해제 노드를 지난 것으로 보고 `nav_off_route`로 섰다.
- **경로가 패치의 스퍼로 이어질 때 그 패치에서 대기**: 해제 노드가 패치(위 합류점 경우 포함)이고 경로상 다음이 그 패치의 스퍼 끝이면, 패치 가운데가 아니라 패치 앞 가장자리(스퍼 갈림 전)에서 선다. 다음 해제를 받으면 다시 가면서 스퍼로 들어간다. 패치 가운데에 서면 스퍼 갈림을 이미 지나 들어갈 수 없었다.
- 패치 위 교차 + 스퍼(도안의 노랑)를 S자 선 쪽에서 지나면, 교차 처리 때문에 스퍼에 한 번 들어갔다 되돌아 나온다(탐색 때와 같은 동작). 시간만 조금 더 든다.

## 서버 주문으로 움직이기 (serve)

**선반 작업(`--tasks`)**: 주문의 끝 동작(`action_at_end`)이 `load`(집기)·`unload`(놓기)·`observe`(보기만)이고 경로가 그 선반의 스퍼 끝에서 끝나면, 도착한 뒤 카메라로 칸을 보고 작업한 다음 결과(`agv/{id}/task`)와 선반 상태(`agv/{id}/shelf`, 작업 전·후)를 보낸다. 작업 중 상태는 `WORKING`, 들고 있는 물건은 상태의 `carrying`. 형식은 [docs/protocol/shelf-task.md](../docs/protocol/shelf-task.md)(로봇 쪽 제안, 서버와 맞추면 `link/task_msgs.py`만 고침). 실물에서는 칸 보기와 1·5번 자세까지 되고, 집기·놓기 팔 동작은 팔 담당이 `agv/task/grip.py`에 `grip(cmd) -> (ok, reason)`을 넣으면 쓰인다(`cmd`는 `task/arm_driver.py` 설명, 그 전에는 `arm_unavailable`로 실패). `--tasks`가 없으면 끝 동작은 지금처럼 무시한다. 시뮬레이션은 `python3 sim/mat/task_demo.py`(아래 테스트).

서버(브랜치 `feature/server-communication`)가 MQTT로 보내는 주문을 받아 `goto`와 같은 코드로 움직이고, 상태·정지 이벤트를 보낸다. 토픽과 주문 형식은 설계 문서 3장, 정지 이벤트는 서버 브랜치의 제안(`server/docs/segment_recovery_proposal.md`)을 따른다.

```bash
pip3 install --user "paho-mqtt<2"     # 젯슨(Python 3.6)은 2.x가 안 깔림. 노트북은 아무 버전
MQTT_HOST=<브로커 PC IP> python3 -m agv.explore --mode serve --map maps/mat_ssafy_v3.json --start N01 --enable-motors --view
# 선반 작업까지: --tasks
```

- 로봇을 `--start` 노드 조금 앞(라인 위)에 놓으면 서서 첫 주문을 기다린다(상태 `IDLE`, `last_node`가 그 노드). 첫 주문의 첫 노드는 `--start`여야 하고, 다음 새 작업은 이전 작업의 마지막 노드에서 시작해야 한다. 스퍼 끝에서 시작하는 주문(`D_P_red, P_red, ...`)은 그 스퍼에 주차해 있을 때만 된다(처음부터 스퍼 끝에 놓고 시작하는 건 아직 안 됨).
- 로봇 ID는 젯슨마다 `python3 -m agv.tools.robotcfg init physical-1`로 정한 값(또는 `--robot`, 환경 변수 `AGV_ROBOT_ID`). 실물은 `physical-<번호>`, 서버의 가상 로봇은 `sim-`으로 시작한다. 브로커 주소·인증은 서버와 같은 환경변수(`MQTT_HOST`, `MQTT_PORT`, `MQTT_USERNAME`, `MQTT_PASSWORD`, `MQTT_TLS_CA`)나 config `link` 항목(`host`, `port`, `waiting`, `state_hz`, `link_loss_s`, `resume_after_reconnect`, `battery`)으로 준다.
- **서버 없이 실물 1대 시험**: 노트북에서 브로커(`mosquitto -v`)를 띄우고, 젯슨에서 위 serve 명령(`MQTT_HOST=<노트북 IP>`)을 띄운 뒤 노트북에서 배차기만 돌린다. 로봇의 첫 상태를 받으면 주문을 보내고, `rear_clear`를 받을 때마다 다음 주문을 보낸다(예약·충돌 방지는 안 함, 1대용). 보낸 주문은 `data/link_demo/dispatch.jsonl`에 남는다.
  ```bash
  python3 sim/link_demo.py --dispatch-only --robot-id physical-1 --host 127.0.0.1 \
      --dispatch N01,J02,J07,N03 --then N03,N02,N07,N01
  mosquitto_sub -h 127.0.0.1 -t 'agv/physical-1/#' -v     # 다른 창에서 상태·이벤트 보기
  ```
- 시간 제한이 없다(`--max-time`으로 줄 수 있음). Ctrl+C로 끝내면 `conn`에 `offline`을 남긴다. 프로그램이 죽거나 와이파이가 끊기면 브로커가 15초쯤 뒤 LWT로 `offline`을 대신 보낸다.

| 토픽 | 방향 | 내용 |
| --- | --- | --- |
| `agv/<id>/order` | 받음, QoS 1 | 주문 `{order_id, seq, map_id, nodes, released_until, action_at_end}` |
| `agv/<id>/state` | 보냄, QoS 0, retained, 5Hz(바뀌면 바로) | 아래 |
| `agv/<id>/event` | 보냄, QoS 1 | 해제 노드에 서면 `rear_clear` 한 번 |
| `agv/<id>/conn` | 보냄, QoS 1, retained | `online` / `offline`(LWT) |

주문 처리(`link/orders.py`):

- 맵이 다르면(`map_id`가 `<맵 map_id>@v<version>`과 다름) 거절. 같은 `(order_id, seq)`가 같은 내용으로 다시 오면 무시(QoS 1 중복), 내용이 다르면 거절.
- 새 작업은 `seq` 1, 같은 작업의 다음 주문은 `seq`+1이고 `nodes`·`action_at_end`는 그대로, `released_until`만 더 앞으로. 서 있을 때 받으면 바로 출발하고, 가는 중에 받으면 멈추지 않고 이어 간다.
- 거절은 이벤트로 보내지 않고 상태의 `rejected`에 싣는다(서버가 이벤트 토픽에서 `rear_clear` 아닌 것을 받으면 오류로 보기 때문).
- 해제 노드가 중간 노드(`V_*`)면, 그 앞 노드를 지난 뒤 엣지 길이만큼 가서 선다(중간 노드는 눈에 안 보이므로 이동거리로).

상태 메시지:

```json
{"ts": 1794816609.4, "map_id": "mat_ssafy_v3@v0", "robot_session": "9a9b77ec8f674d34",
 "last_node": "S2", "edge": ["S2", "V_E15"], "next_node": "V_E15", "progress": 0.42, "dir": "fwd",
 "pose": {"x": 855.7, "y": 17.3, "th": -173.6, "src": "interp"},
 "status": "MOVING", "carrying": null, "battery": null,
 "order_id": "T1", "seq": 2, "released_until": "V_E15", "error": null, "rejected": null}
```

- `status`: `IDLE`(주문 없음·작업 끝) / `MOVING` / `WAITING`(해제 노드에서 다음 해제를 기다림) / `ERROR`(`error`에 이유: `link_lost`, `nav_off_route`, `nav_spur_missed`, 종료 이유 등).
- `pose`: 맵 좌표 mm, `th`는 맵 x축에서 잰 도(맵 `coordinate_frame` 그대로). 노드를 지날 때 맞추고 그 사이는 이동거리로 엣지 모양 위에 놓는다(`src: interp`). 노드에 서 있으면 `node`, 처음 놓인 자리는 `start`, 스퍼를 드나드는 중이면 `spur`(부모 노드 위치). 가상 매트에서 실제 위치와의 차이는 중간값 2cm, 90%가 5cm 안이었다.
- runner는 합류 뒤 30cm 동안 교차인지 보느라 이벤트를 보류한다. 그동안 Navigator 위치가 늦어서, 자세는 경로를 따라 이동거리로 이어 붙인다(해제 노드를 넘지 않음).
- `battery`: config `link.battery`에 INA219 주소를 넣었을 때만 값이 있다(`link/battery.py`, 보드에 센서가 있는지 현장 확인 필요). 없으면 `null`.

정지와 끊김:

- 해제 노드에 서면 `rear_clear`를 보낸다: `{type, event_id, robot_session, order_id, seq, map_id, stopped_at, cleared_resources}`. `cleared_resources`는 서버 `plan_segment` 규칙을 그대로 흉내 내 계산한다(구간 노드·엣지·공유 구역 - 다음 구간과 겹치는 것). 대기 노드를 정하는 법은 config `link.waiting`: `zones`(맵 waiting 구역, 기본) 또는 `all`(서버 주문 시연이 쓰는 "모든 노드가 대기 지점" 가정). 서버 쪽과 같아야 서버가 받는다.
- 브로커 연결이 1초(`link_loss_s`) 넘게 끊기면 그 자리에 선다(라인 추종 중이면 바로, 회전·후진·주차 중이면 끝나는 대로). 다시 붙어도 저절로 가지 않고 `ERROR`/`link_lost`로 남는다. 재동기화 규약이 정해지기 전까지의 안전한 기본값이며, `link.resume_after_reconnect: true`면 남은 해제 구간을 이어 간다.

집에서 시험(가상 매트 + 실제 브로커): `sim/link_demo.py`. mosquitto를 띄우고 `python3 sim/link_demo.py --dispatch ...`이면 작은 배차기가 구간별로 해제를 보내며 끝까지 돌린다. 서버의 트윈 브리지에 이어 언리얼에서 보려면 로봇 ID를 `sim-r1`(기본값)로 둔다.

서버·트윈과 정해야 할 것(현재 코드가 가정한 것):

1. **상태 형식**: 설계 문서 형식(`pose` mm·`th`, `last_node`, battery 0~1)으로 보낸다. 트윈 요청서는 최상위 `x`, `y`(m)·`yaw`·`current_node`·battery %였는데, 서버 브리지가 이미 변환한다. 서버 브리지는 `battery`가 없으면 상태를 통째로 버리고, 자세는 시험용 맵 ID(`twin-validation-v1`)일 때만 넘긴다 - 실제 맵 ID를 받게 바꿔야 한다.
2. **rear_clear 자원 계산**: 로봇이 서버 내부 자원 이름과 다음 구간까지 알아야 해서 서로 엇갈리기 쉽다. 로봇은 `stopped_at`만 보내고 서버가 계산하자고 제안.
3. **로봇 방향**: 서버 경로 계산이 로봇이 어느 쪽을 보는지 모른다. 패치 가운데·스퍼 끝에 서 있으면 로봇이 알아서 유턴하지만, 그 밖의 노드(갈림길 앞 등)에서 뒤로 가는 경로를 받으면 출발한 뒤 경로를 벗어났다고 보고 선다(`nav_off_route`). 상태의 `dir`·`edge`를 경로 계산에 쓰거나, 작업 끝 지점을 패치·스퍼 끝으로 두면 된다.
4. **도착·작업 이벤트**: 상차·하차 완료, 실패 이벤트 형식이 없다. 지금은 `rear_clear`와 상태(`status`, `error`, `rejected`)뿐.
5. **로봇 ID·대기 지점**: 서버 시뮬레이션은 `sim-` ID만 받는다. 매트 맵의 대기 지점은 스퍼 끝뿐이라 구간이 길다(서버 시연은 모든 노드를 대기 지점으로 봄).
6. **끊김 뒤 재개**와 **재시작 동기화**(로봇이 재부팅하면 위치를 모름).

## 검출 방식과 조정 값

카메라는 앞 바닥을 비스듬히 본다(화면 아래 = 가까움). 스캔 영역에 가로줄 14개를 긋고 줄마다 라인 조각을 찾는다.

- **라인**: 어둡고 채도 낮은(`s_max`) 픽셀. 아주 어두운 픽셀은 채도와 상관없이 라인으로 본다. 밝기 문턱은 프레임마다 정한다(`v_auto`): 스캔 영역 밝기의 3% 지점을 테이프, 70% 지점을 매트로 보고 테이프 + 0.25 x (매트 - 테이프)(`v_split`)보다 어두우면 라인, 0.13(`v_dark_split`)보다 어두우면 채도와 상관없이 라인. 테이프가 안 보여 둘 차이가 작으면 매트의 35%로 둔다. 조명을 옮기면 테이프가 어두운 방 20에서 밝은 곳 90까지 바뀌어 고정 문턱(`v_max`·`v_dark`, `v_auto: false`일 때만 씀)으로는 한쪽에서 선을 아예 못 보거나 패치 가장자리를 선으로 봤다. 어두운 곳은 노이즈로 채도가 튀어서, 이 처리가 없으면 선이 두 조각으로 쪼개진다.
- **색 패치**: 화면 아래쪽(`patch.region_top`부터)에서 그 색 비율이 `on_frac`을 넘으면 진입 이벤트를 낸다.
- **갈림길**: 조향 줄(`line.control_row`, 차체 바로 앞)에서 조각 수가 바뀌는 순간을 본다.
  - 1개에서 2개로 바뀔 때 두 조각이 붙어 있고 간격이 벌어지면 **갈라짐**이다. 이때 탐색 정책이 갈 쪽을 고른다.
  - 2개에서 1개로 바뀔 때 두 조각이 붙어 있었으면 **합쳐짐**이다.
  - 옆에서 다른 선이 들어오거나 나가는 경우(간격이 좁아지거나 처음부터 멂)는 무시한다.
  - 갈라짐 이벤트의 `onset`(간격/라인폭 비율, 간격 변화 px)을 보고 `junction.split_*` 값을 조정한다. 시뮬레이션에서 갈라짐은 비율 1.2~1.7·변화 +15 이상, 옆 선 진입은 비율 1.8 이상·변화 음수였다.
- 앞쪽에 갈래 모양이 보이는 것(`fork_ahead`)만으로는 방향을 정하지 않는다. 합류 지점에 옆 가지로 들어갈 때도 화면상 똑같이 보여서, 그걸 믿으면 반대 가지로 역주행한다(시뮬레이터에서 실제로 겪음).
- **X자 교차**: 합류가 나면 바로 기록하지 않고 `junction.cross_window_mm`(300mm) 동안 보류한다. 그 안에 선이 다시 갈라지는데 다른 선이 내가 있던 쪽으로 빠져나가면 교차다. 판단은 두 가지로 한다. 하나는 그쪽 조각이 더 비스듬한지, 다른 하나는 그 조각 기울기가 합류 직전 다른 선 기울기와 이어지는지다. 교차면 `cross` 이벤트를 남기고 곧은 선을 따라간다. 아니면 보류한 합류를 기록하고 보통 갈림길로 처리한다. 보라 패치 뒤 렌즈처럼 합류 직후 같은 쪽으로 다시 갈라지는 경우가 여기에 해당한다.
- **급한 가지(V자)**: 모서리 곡선 위에서 급하게 꺾여 나가는 가지는 갈라지는 모습이 안 보이고, 옆에서 들어와 내 선에 붙는 선(합류 모양)으로 보인다. 옆 선이 가파르게 들어와 `junction.vee_max_frames`(5) 안에 붙고, 붙은 뒤 내 선이 그 선 쪽으로 `vee_cont_px`(줄당 4px) 이상 휘어 나가면 그쪽에 급한 가지가 있다고 본다. 반대쪽으로 휘면 옆에서 붙는 T자 합류다(빨강 앞 합류처럼). 탐색 정책이 그 가지를 고르면 차체 중심이 만나는 점에 올 때까지 간 뒤 그쪽으로 제자리 회전해 가지를 탄다(`note` `vee_pivot`·`vee_done`). 시뮬레이션에서 S자 선 갈림길은 휨 9~13, 빨강 앞 T자 합류는 반대 방향 22 정도였다.
- **속도 보정(패치)**: 화면의 한 가로줄은 바닥의 한 선이다. 패치 앞 가장자리가 그 선을 지나는 순간부터 뒤 가장자리가 지날 때까지 로봇은 정확히 패치 길이만큼 움직이므로, 그사이 적분한 모터 명령으로 패치 길이를 나누면 실제 속도가 나온다. 렌즈 왜곡이나 카메라 각도와 상관없다. 가로줄 10개에서 따로 재 중앙값을 쓰고, 지나는 동안 크게 돌았거나(곡선, `speedcal.turn_max`) 줄마다 값이 흩어지면(`max_spread`) 버린다. 첫 측정은 그대로, 그 뒤로는 40%씩 섞는다. 시뮬레이션에서 실제 속도가 설정보다 20% 느리고 1분에 5%씩 더 느려질 때, 패치 사이 거리 오차가 보정 없이는 +30%, 보정하면 중앙값 2% 안팎이었다. 곡선에서 궤도가 미끄러져 덜 도는 것은 주행 중에는 보정하지 않고, 맵을 만들 때 같은 노드로 돌아온 고리로 맞춘다(`trace.jsonl`, [모양 계산](../mapping/README.md#모양-계산-주행-기록)).
- **스퍼(T자)**: 조향 줄의 선 조각이 한쪽으로만 라인폭의 3배 넘게 넓어지고, 조향 줄에서 3줄 위·아래는 보통 폭 선 하나뿐일 때(엄격 기준) `tee`로 기록한다(2프레임 연속). 띠가 얇은지 보는 이 조건으로 곡선 합류를 스퍼로 잘못 보는 것을 거른다. 비스듬히 만난 스퍼는 띠가 위·아래 줄 한쪽에 걸치거나 이음 자리가 한 줄에서 살짝 끊겨 엄격 기준이 한 프레임씩만 맞으므로, 좁은 틈(라인폭 0.6배, `tee.join_gap_k`)은 잇고 위·아래 줄은 하나만 보통 폭이어도 되는 느슨 기준도 본다. 연속 프레임은 엄격이나 느슨으로 세되 하나는 엄격이어야 한다(느슨만으로 세면 갈림길 시작을 스퍼로 봄). 라인 추종은 넓은 조각에서 내 선 쪽 가장자리를 쓰므로 스퍼 쪽으로 끌려가지 않는다.
- **따라갈 조각 고르기**: 바로 앞 프레임의 라인 위치에서 가장 가까운 조각을 따라간다. 바로 앞 프레임에 라인을 봤으면 화면 폭의 20%(`follow.track_jump_frac`)보다 먼 조각으로는 넘어가지 않는다. 조향 줄 라인 폭의 30%(`min_w_k`)보다 가는 조각도 라인으로 치지 않는다(어두운 조명에서 패치 가장자리가 가는 어두운 띠로 잡힘). 매트 밖 바닥으로 빼 둔 조각도 라인 추종에서는 후보로 본다. 옆 가지와 붙어 화면 끝까지 넓어진 선이 바닥과 함께 빠지면 따라갈 선이 사라지기 때문이다.
- **라인을 놓쳤을 때**: 마지막 라인 위치에서 갑자기 먼 조각은 라인으로 치지 않는다. 화면 옆 끝에 붙은 조각은 화면 폭의 30%(`follow.jump_frac`), 나머지는 50%(`max_jump_frac`)보다 멀면 버린다. 급커브에서 라인이 화면 밖으로 나간 순간 매트 밖 바닥(먼 줄이나 반대편 끝)을 라인으로 잡아 계속 그쪽으로 도는 것을 막는다.
  - 놓치기 직전 라인이 화면 왼/오른쪽 30%(`edge_frac`) 안에 있었으면 급커브로 나간 것으로 본다. 그쪽으로 제자리 회전(`recover.pivot_speed`)하며 조향 줄과 그 아래 줄에서 라인을 다시 찾는다(`note` `line_search`·`line_search_done`). `search_timeout_s`(4초) 안에 못 찾으면 멈춘다.
  - 가운데에서 놓쳤으면 전처럼 직전 명령을 조금 이어 가다 `lost_timeout_s`(1초) 뒤 멈춘다(`gap reason=line_lost`).
  - 옆으로 나가며 사라진 선은 막다른 길(선 끝)로 보지 않는다.
- **안쪽 궤도 하한**: `follow.min_track`(기본 0, 끔)을 주면 라인 추종 명령에서 안쪽 궤도가 그 아래로 내려가지 않게 좌우를 같이 올린다(회전 정도는 그대로). 실물에서 안쪽 궤도를 0.07까지 낮춘 급회전이 멈췄다.
- **회전 중 멈춤**: 궤도 차량은 급하게 돌 때 바닥과 비벼야 해서 직진보다 힘이 더 든다. 실물 주행 세 번 모두, 바깥 궤도 0.4~0.6 / 안쪽 -0.2~0.1로 도는 명령에서 로봇이 그대로 서 있었다. 좌우 명령 차이가 0.2 이상인데 화면이 0.5초 동안 거의 안 바뀌면 출력을 프레임마다 조금씩 올리고(최대 1.8배, 명령 최대 0.95), 움직이면 천천히 내린다(`stall`, `note` `stall_boost`). 이동거리 적분은 올리기 전 명령으로 한다. 회전에 실제로 얼마가 필요한지는 `camtool turn --enable-motors`로 본다.
- **이벤트 위치**: `geom.ctrl_ahead_mm`·`geom.patch_ahead_mm`만큼 앞당겨, 차체 위치가 아니라 판정한 바닥 지점으로 기록한다. 확정이 몇 프레임 늦어도 처음 감지한 프레임 기준이다.

## 막다른 길에서 되돌아 나오기

갈림길이나 교차에서 고른 쪽으로 60cm 안에 선이 끝나면 막다른 길(스퍼)로 보고 되돌아 나온다. drive·ask 모드에서만 동작한다.

1. **감지**: 조향 줄부터 위쪽 줄에 선이 하나도 없고 아래쪽 줄에만 있는 상태가 3프레임 이어지면 선 끝으로 본다. 선을 완전히 놓친 지 0.3초가 지나도 같다. 멈추고 `dead_end`를 기록한다. 스퍼 길이는 갈림길에서 선 끝까지다.
2. **후진**: 화면 속 선 기울기로 방향을 잡으며, 차체 중심이 갈림길 지점에 올 때까지 후진한다. 거리는 모터 명령으로 잰다.
3. **회전**: 스퍼 반대쪽으로 제자리 회전한다. 스퍼 선이 화면 가운데를 벗어난 뒤 다른 선이 가운데에 오면 멈추고 다시 따라간다.
4. **기억**: 탐색 정책은 그 갈림길을 막다른 길로 기억한다. 다음에 만나면 묻지 않고 반대쪽으로 가고 `tee`로 기록한다. 맵에는 스퍼 길이가 남는다.

곡선에서 합류한 직후의 스퍼처럼 비스듬히 만나는 스퍼를 갈림길로 착각해도, 이렇게 맵을 고치지 않고 탐색을 이어 간다. 나중에 스테이션에서 스퍼로 빠졌다 나오는 동작에도 같은 후진·회전을 쓸 수 있다.

현장에서 확인할 것:

- **선 끝 너머 바닥**: 매트 밖 카펫이 어두우면 선으로 잡혀 끝을 못 알아본다. 스퍼 끝에서 `snap`을 찍어 `line_mask.png`에 카펫이 하얗게(선으로) 나오지 않는지 본다. 나오면 `line.v_max`를 낮추거나 스퍼 끝에 흰 종이를 댄다.
- **후진 거리**: 궤도가 후진할 때 전진과 속도가 다르면 갈림길보다 덜 또는 더 물러난다. 회전 뒤 선을 못 찾으면 `recover.back_extra_mm`를 조정한다.

## 맵(테이프) 배치 규칙

시뮬레이터에서 탐색이 막혔던 경우를 바탕으로 정했다. 카메라는 차체 앞 약 12cm를 보고 따라가므로, 곡선을 도는 중에는 차체가 선보다 늦게 돈다.

- **스퍼**는 직선 구간에 직각으로 붙이고, 모서리·합류·분기·교차에서 15cm 이상 띄우는 게 가장 좋다(새 매트 N01은 모서리 끝에서 17cm, 시뮬레이션은 지금 검출로 통과. 실물에서 확인). 곡선에서 합류한 직후의 스퍼는 아직 꺾는 중인 로봇에게 비스듬한 가지로 보인다. 이 경우 탐색은 막다른 길 되돌아 나오기로 이어 가지만, 매번 한 번씩 들어갔다 나오느라 시간이 든다.
- **갈림길**은 진행 방향에서 30도 이내로 완만하게 갈라지게 하는 게 가장 안전하다. 모서리 곡선 위에서 급하게 꺾여 나가는 가지(도안의 S자 선 시작점)는 V자 처리로 들어가지만, 제자리 회전에 기대므로 실물에서 먼저 확인한다. 회전 뒤 원래 곡선을 다시 타면 `recover.pivot_center`나 회전 속도를 조정한다.
- **교차**는 30도 이상 각도로 지나가게 하고, 교차 위에 스퍼를 두지 않는다.

## 이벤트 로그

`data/runs/<시각>/events.jsonl`에 한 줄에 하나씩 기록된다. 형식은 `topo/events.py` 맨 위에 있다.

```json
{"ts": 1730700000.85, "seq": 1, "type": "patch", "odo_mm": 127.0, "color": "orange"}
{"ts": 1730700012.95, "seq": 3, "type": "split", "odo_mm": 1735.2, "choice": "left", "cmd": "left", "onset": {"ratio": 1.23, "trend": 16.0}}
{"ts": 1730700014.10, "seq": 5, "type": "merge", "odo_mm": 2013.4, "from_side": "left"}
```

같은 폴더의 `trace.jsonl`에는 프레임마다 이동거리(`o`)와 좌우 모터 명령 차이 적분(`y`, 그중 제자리 회전 몫 `p`)이 남는다. 맵 빌더가 이것으로 실효 궤도 폭을 맞추고 맵 모양(노드 좌표·엣지 곡선)을 계산한다([mapping/README.md](../mapping/README.md#모양-계산-주행-기록)). passive 모드에서는 모터 명령이 없어서 남기지 않는다.

`odo_mm`은 모터 명령 × 속도를 적분한 추정 이동거리에 판정 지점까지 거리(`geom`)를 더한 값이다. 속도는 `patch.length_mm`가 있으면 패치를 지날 때마다 다시 잰 값(`note` `speed_cal`)을 쓴다. passive 모드에서는 `null`이고, 이때 빌더가 시간 × 속도로 대신 계산한다. 교차는 `cross`(다른 선이 들어온 쪽 `from_side`), 스퍼는 `tee`(`side`)로 남는다.
