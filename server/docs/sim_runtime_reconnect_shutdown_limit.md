# 가상 런타임 재연결 중 종료 지연

격리 시뮬레이션의 `SimRuntime.reconnect()`는 기존 수신기와 workflow 정리,
새 수신기의 생성·TCP 연결·MQTT 구독 확인을 런타임 잠금 아래에서 수행한다.
따라서 이 과정의 네트워크 또는 정리가 지연되면 `stop()`도 같은 잠금을
기다린다. 종료 요청이 들어온 시점에 `_stopped`나 workflow의 `_stopping`이
즉시 설정된다는 보장은 없다. TCP 연결과 구독에는 설정된 제한이 있지만,
기존 workflow 종료나 콜백 정리까지 포함한 종료 전체의 고정 상한은 없다.

격리 aMQTT와 테스트 전용 새 DB에서 기존 수신기를 끊은 뒤 재연결 클라이언트의
`connect()` 진입을 이벤트로 멈추고 다른 스레드에서 `stop()`을 호출했다.
0.5초 관찰 동안 종료는 반환하지 않았고 `_stopped`와 workflow의 `_stopping`은
모두 false였다. 이때 테스트 작업은 단절로 복구 게이트의 로컬 차단 집합에
있었다. 연결 대기를 풀자 재연결이 종료되고 `stop()`도 완료됐다. 이는 해당
주입 조건에서의 관찰이며 모든 재연결 경합이나 실제 장비 정지의 증명이 아니다.

정상 단절 경로의 게이트 무효화는 해당 가상 작업을 차단하고, 구간 진행은
별도의 복구 검사를 사용한다. 재연결 자체가 복구 승인이나 물리 상태 증명은
아니다. 그러나 종료 대기 중 재연결이 완료되면 런타임 잠금을 기다리던 종료와
다른 API 호출의 획득 순서는 보장되지 않는다. 따라서 **종료 요청만으로 새로운
가상 작업이나 발행이 즉시 차단된다고 가정하면 안 된다.** 이미 발행된 메시지도
회수할 수 없다. 이 가상 런타임을 실물 로봇의 정지 또는 안전 인터록으로
사용하지 않는다.

해결하려면 재연결별 세대와 종료 요청을 독립적으로 동기화하고, 네트워크 I/O를
잠금 밖으로 옮긴 뒤에도 중단된 연결·콜백이 이전 DB 소유권이나 새 workflow를
사용하지 못하도록 수명과 cleanup을 보장해야 한다. 단순히 잠금을 제거하면
종료가 DB 소유권을 놓은 뒤 늦게 연결된 콜백이 DB를 사용하는 경합이 생길 수
있다. 이 변경은 구현되지 않았으며, 단절·연결 성공/실패·구독 대기·동시 종료·
중복 재연결과 발행 fence의 별도 종단 시험이 필요하다.
