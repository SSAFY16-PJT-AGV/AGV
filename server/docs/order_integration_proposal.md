# 작업 배정·구간 예약·주문 통합: 구현 경계

설계 기준: `docs/project-plan` 브랜치의 `docs/design.md` 3장, 4장,
7장. 주문 MQTT 토픽 및 본문은 해당 설계의 `agv/{id}/order`, QoS 1과
`order_id`, `seq`, `map_id`, `nodes`, `released_until`, `action_at_end`를
사용하며, MQTT 필드를 임의로 추가하지 않는다.

## 내부 구현 선택

- 작업 배정, 자원 점유, 발행할 주문의 기록은 SQLite 트랜잭션 하나로
  저장한다. 서버 재시작이나 통신 단절로 점유를 자동 해제하지 않는다.
- 반대 방향으로 통행하는 같은 물리 엣지는 같은 점유 자원으로 취급한다.
  우선 모든 엣지를 단일 차선처럼 보수적으로 예약한다. 경로는 다음
  대기 지점까지 확보하며, 안전한 정차점이 확인되지 않으면 거부한다.
- 발행 시도 전 주문의 상태를 먼저 기록한다. 그 뒤 결과가 불확실하거나
  서버가 중단되면 자동 재발행하지 않고 예약을 유지한다. 브로커의 PUBACK은
  로봇이 주문을 받거나 수행했다는 확인이 아니다.
- 운행 허가는 기본적으로 꺼져 있다. 먼저 분리된 로컬 브로커 및 가상
  장치에서만 테스트한다. 실제 장비를 움직이는 코드는 사람이 실물·환경을
  확인하기 전 자동으로 켜지지 않는다.

## 실제 주행 연동 전 팀 협의와 검증

설계 문서는 로봇의 유효 위치·연결 신선도, 주문 중복/시퀀스 복구,
후단 이탈 이벤트의 식별 및 인증, 맵의 점유 구역 경계·정지거리, 재부팅
후 동기화의 세부 규격을 정하지 않았다. 이 조건을 추측해 자동으로 위치를
확정하거나 예약을 해제하지 않는다. 서버·로봇·맵 담당자가 규격을 확정하고
안전 정지·중복·충돌·복구를 실물과 독립된 테스트를 거쳐 검증해야 한다.

실제 FastAPI 관제 화면과의 작업 요청, 인증·인가 및 TLS/접근 제어도 별도
설계가 필요하다. 이 문서는 내부 구현 제한과 가정을 제시하며 새로운 MQTT
필드나 최종 팀 프로토콜을 선언하지 않는다.
