# 다음 구간 계획과 후단 이탈 기록: 격리 시뮬레이션

이 모듈은 [팀 협의용 후단 이탈·복구 제안](segment_recovery_proposal.md)을
시뮬레이션에서 시험한다. JSON 이벤트와 회복 증명만으로 실제 로봇의 위치,
정지나 후단 이탈을 확인할 수 없다. MQTT 이벤트 인증·인가와 물리 안전
판정도 없으므로 실물 브로커·로봇과 연결하지 않는다.

`SegmentProgress(store, map_data, simulation_enabled=False, recovery_gate=None)`는
기본적으로 비활성화다. 별도 격리 시뮬레이션에서만 명시적으로 켜고,
같은 SQLite DB의 `RecoveryGate`를 제공해야 한다. `initialize()`는
`progress_orders`와 `progress_events` 표를 생성한다. 최초 주문의 원본인
`allocation_outbox`는 보존하며, 다음 이벤트를 받아들이는 트랜잭션에서
순번 1을 이력에 복사한다.

`advance(robot_id, event, retained=False)`는 `rear_clear` 이벤트에 지정된
로봇·부팅 세션·맵·작업·순번·정지 대기점을 회복 증명 및 DB와 비교한다.
명시적으로 retained 표시된 이벤트는 거절한다. MQTT 3.1.1에서 이 수신
플래그만으로 발행 당시 retain 여부를 항상 알 수 없으므로, 발행자와
브로커 측에서도 이벤트를 retain 없이 보내도록 별도 보장이 필요하다.
`sim-` 접두사는 실제 네트워크나 발행자의 격리를 증명하지 않는다.

현재 점유가 맵에서 계산한 기존 구간과 정확히 일치하고, 이벤트의
`cleared_resources`가 **이전 구간에서 다음 구간과 겹치지 않는 모든 자원**을
정확히 열거할 때만 진행한다. 이탈 증명된 자원의 해제와 다음 대기점까지의
전체 구간 예약, 새 순번 주문의 pending 기록, 이벤트 ID와 본문 digest의
기록을 단일 트랜잭션으로 수행한다. 자원 충돌이나 불일치 시 모두 롤백하고
기존 점유를 유지한다. 다음 구간과 겹치는 자원은 계속 점유한다.

동일 로봇의 같은 이벤트 ID·동일 본문은 인증된 같은 세션의 유효 증명
아래 중복 결과를 반환하고 변경하지 않는다. 같은 ID·다른 본문은 거절한다.
이전 증명이 만료되거나 새 순번·세션의 증명으로 교체된 뒤 도착한 중복은
상태를 변경하지 않고 안전하게 거절한다. 과거 이벤트를 단순 조회하는 것과
현재 구간을 해제할 권한은 다르며, 과거 증명을 진행 권한으로 사용하지 않는다.
이전 세션·순번·맵, 미승인 회복과 아직 시도하지 않은 순번은 거절한다.
브로커 확인이 불확실한 `uncertain` 주문은 해당 순번과 대기점에 대한 별도의
유효한 시뮬레이션 회복 증명과 이탈 이벤트가 함께 있을 때만 진행 가능하다.
이 경우에도 기존 주문을 `acked`로 바꾸지 않는다.
마지막 대기점이면 `finished`로 기록하되 이탈한 이전 자원만 해제하고
마지막 노드 점유를 남긴다. `finished`는 상하차나 작업 완료가 아니다.

`get_order(task_id, seq)`는 저장된 후속 주문을 조회한다.
`mark_attempted(task_id, seq, robot_session, expected_payload, expected_resources)`와
`mark_broker_acked(...)`는 호출자가 제공한 기존 순번·정지점 회복 증명과
주문·맵·현재 점유를 동일 트랜잭션에서 확인하고 각각
`pending → uncertain → acked`로 변경한다. 실제 MQTT 발행은 하지 않는다.
브로커 PUBACK은 로봇 수신·실행의 증거가 아니고, 오류·불확실 상태에서도
자동 재발행이나 점유 해제를 하지 않는다. 다음 순번의 후단 이탈을 받기
전에는 그 순번과 대기점에 대한 새 회복 증명이 필요하다.

맵의 공유 구역은 수동으로 검증된 완전한 자원 표현이라고 가정한다. 맵
fingerprint 비교는 다른 내용의 맵을 혼용하지 않게 할 뿐, 맵 자체가 물리적으로
안전함을 증명하지 않는다. 사람이 대기점·차체 길이·정지거리·이탈 기준을
확인하고 로봇의 부팅 세션·이벤트 ID·송신 인증 및 중복 처리를 합의해야 한다.
