# 구간 진행·중복·복구 규격 제안 (격리 시뮬레이션)

`docs/project-plan`의 설계 문서 v0.2는 주문의 `order_id`, `seq`,
`map_id`, `nodes`, `released_until`, `action_at_end`와 QoS 1 이벤트 토픽을
정의하지만, 후단 이탈·중복 처리·재시작 동기화의 상세 메시지는 정의하지
않는다. 아래는 **팀 협의 전 임시 제안**이며 실물 로봇에 대한 운행 승인이 아니다.

## 후단 이탈 이벤트 제안

`agv/{robot_id}/event`에 QoS 1, retain 없이 아래 JSON을 발행한다. `robot_id`는
토픽에서 가져온다. `event_id`는 해당 로봇에서 유일한 이벤트 식별자다.

```json
{
  "type": "rear_clear",
  "event_id": "예시-이벤트-ID",
  "robot_session": "예시-부팅-세션-ID",
  "order_id": "예시-작업-ID",
  "seq": 1,
  "map_id": "예시맵@v1",
  "stopped_at": "N3",
  "cleared_resources": [["node", "N1"], ["edge", "예시-서버-자원-ID"]]
}
```

`stopped_at`은 현재 허가 구간의 마지막 대기 노드이며, `cleared_resources`는
로봇 후단이 실제로 벗어났음을 확인한 **현재 점유 자원만** 열거한다. 대기
노드 및 후속 구간과 겹치는 자원은 계속 점유한다. 로봇의 크기·정지거리와
맵으로부터 이 목록을 산출하는 실제 방법은 팀이 정해야 한다. 단순 도착,
MQTT PUBACK, 온라인 표시 또는 과거 retained 상태는 이탈 증거가 아니다.

이벤트 ID와 본문을 영속 저장한다. 같은 ID·같은 내용은 중복으로 처리하고,
같은 ID·다른 내용, 다른 로봇·맵·세션, 오래되거나 예상 밖의 주문 순번은
거절한다. 이벤트 검증·자원 변경·다음 구간의 전체 예약·다음 순번 주문은
한 DB 트랜잭션으로 처리한다. 다음 구간을 확보할 수 없으면 기존 안전 점유를
유지하고 발행하지 않는다.

## 주문 중복 제안

로봇은 `(order_id, seq)`별 수신한 주문 내용의 digest와 처리 상태를 영속
기록한다. 같은 순번·같은 내용의 재수신은 다시 실행하지 않고, 같은 순번의
다른 내용과 순서 역행·미승인 맵을 거부한다. 브로커의 QoS 1 확인은 로봇이
명령을 수신했거나 실행했다는 의미가 아니다. 전송 결과가 불확실하면 자동
재발행하지 않고 점유를 유지한다.

## 재시작 복구 제안

서버 재시작 시 모든 작업·주문 이력·점유를 보존하고, 이전 주문 자동 발행과
점유 해제를 막는다. 재동기화에는 새 1회용 challenge와 로봇의 부팅 세션,
정지 상태, 현재 노드, 맵 버전, 마지막 적용 주문 ID·순번·digest를 대조하는
절차를 제안한다. challenge와 응답의 실제 토픽·JSON 상세, 인증·인가,
로봇이 재부팅 직후 물리 상태를 확인하는 방법은 팀 합의가 필요하다.

가상 시험은 임시 DB와 별도 루프백 브로커에서만 진행한다. `sim-` ID나 토픽
접두사만으로 장치나 네트워크의 격리를 보장할 수 없다. 실제 장비 연결 전
메시지 출처 인증, 중복 처리, 상태 신선도, 후단 이탈 판정, 안전 정지 및
실측 구간의 검증을 완료해야 한다.
