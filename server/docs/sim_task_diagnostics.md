# 격리 시뮬레이션 작업 진단 조회

기존 인증된 로컬 시뮬레이션 API의
`GET /simulation/tasks/{task_id}/diagnostics`는 현재 런타임에 명시된 한 작업의
저장 상태를 읽는다. 실행 중인 작업을 비롯한 `pending`, `uncertain`, `acked`
주문의 순번과 상태, 배정된 가상 로봇·맵·해제 노드, 점유 자원, 해당 로봇과
작업에 속한 대기 이벤트의 ID·순번을 보여준다. 주문 본문, 이벤트 본문,
로봇 세션, 인증정보와 다른 작업의 이벤트는 반환하지 않는다.

`database_snapshot`의 작업·주문·점유·이벤트는 같은 SQLite 읽기
트랜잭션에서 조회한다. 주문은 최대 100개, 점유는 최대 500개, 이벤트는 최대
100개이며 `*_truncated`가 생략 여부를 나타낸다. `pending`은 아직 전송되지
않은 주문, `uncertain`은 전송 결과 불명, `acked`는 브로커 PUBACK 기록이다.
`acked`는 로봇 수신이나 실행 확인이 아니다.

응답에 포함할 작업 ID와 DB에서 읽는 작업 상태·로봇 ID·맵 ID·해제 노드·
주문 상태·점유 종류·점유 자원 ID는 각각 UTF-8 기준 1~256바이트의 문자열로
제한한다. 이 중 작업 ID가 제한을 벗어나면 요청을 거부하고, 조회한 DB 값이
제한을 벗어나거나 문자열이 아니면 진단을 일반 오류로 종료한다. ID를
일부분만 돌려주지 않는다. 조회한 후속 주문의 순번도 정수여야 한다. 이 제한은
진단 출력 범위를 정하는 것이며 DB의 실제 값, 맵·주문·점유 정합성이나 물리
안전을 검증하지 않는다.

목록 개수와 각 문자열의 바이트 수는 제한하지만, JSON 이스케이프와 HTTP
헤더까지 포함한 응답 전체에 별도의 고정 바이트 상한을 설정한 것은 아니다.
진단 문자열은 임의로 잘라내지 않으며 오류 응답에 DB 내용을 넣지 않는다.

대기 이벤트 ID가 UTF-8 기준 256바이트를 초과하거나 저장된 값이 유효한
문자열이 아니면 `event_id: null`, `event_id_omitted: true`로 표시한다.
식별자를 일부만 잘라 다른 ID와 혼동하지 않는다. 저장된 이벤트 순번이 양의
정수가 아니면 `seq: null`, `seq_omitted: true`로 표시한다. 정상적인 값은
변경하지 않는다. 이벤트 본문과 digest는 읽거나 검증하지 않으며 항상
`pending_events_integrity: "not_checked"`로 표시한다. 따라서 손상되거나
일치하지 않는 저장 메타데이터도 포함될 수 있고, 이 목록은 이벤트 처리나
주행에 사용할 유효한 증거가 아니다.

`command_response_observations`는 선택적 가상 명령 응답 기록의 메타데이터다.
`availability: "not_installed"`는 관련 테이블이 둘 다 없는 기본 DB이고,
`"available"`은 해당 형식의 테이블이 있는 경우다. 일부 테이블만 존재하거나
스키마·트리거·epoch 메타데이터가 올바르지 않으면 진단을 일반 오류로 중단한다.
관측 기능이 활성화된 런타임에서 두 테이블이 모두 없어져도 오류다. 기능이
비활성화된 상태에서 두 테이블이 없는 경우는 이전 기록이 존재한 적이 없음을
증명하지 않으며, 단지 현재 DB 스냅샷에서 찾지 못했다는 의미다.
현재 수신기를 비활성화했더라도 과거 테이블이 남아 있으면 저장된 주장을
조회한다. 한 작업과 그 작업에 설정된 가상 로봇에 속하는 기록만 최대 100건
돌려주며, 나머지는 `truncated: true`로 표시한다.

각 항목의 `claimed_outcome`은 팀 미합의 가상 응답의 주장으로, 정상 값은
`accepted` 또는 `rejected`다. 그 밖의 값은 `null`과
`outcome_unrecognized: true`로 표시한다. 이벤트 ID는 256 UTF-8바이트를
넘으면 `null`과 `event_id_omitted: true`, 순번이 양의 정수가 아니면 `null`과
`seq_omitted: true`로 표시한다. 세션, 주문 digest, 응답 본문과 epoch 값은
반환하지 않는다. 이벤트 본문·digest·송신자 출처는 검사하지 않으며 결과에는
항상 `integrity: "not_checked"`, `kind: "unverified_simulation_claim"`이
붙는다. DB 내용이 손상되거나 임의로 변경된 경우에도 이런 메타데이터가 나올
수 있다.

`epoch_relation`의 `same_at_db_snapshot` 또는 `different_at_db_snapshot`은
관측 행의 epoch, 관측 메타의 epoch, DB에 기록된 복구 epoch를 **그 읽기
스냅샷 안에서 비교한 결과**다. 비교할 값이 없거나 잘못됐거나 관측 행이 메타와
다르면 `unknown`이다. 이는 실행 중인 gate와 원자적으로 비교한 결과도 아니고,
현재 수락·정지·명령 전달·브로커 ACK 전달이나 물리적 안전의 증거도 아니다.
각 epoch는 NUL이 없는 64바이트 소문자 16진 문자열이어야 한다. 관측 메타의
epoch가 이 형식에 맞지 않으면 진단을 중단하고, 관측 행이나 복구 epoch가
잘못되면 비교 결과를 `unknown`으로 표시한다.
같은 프로세스에서 런타임을 재생성할 때 기존 명령 응답 관측 기능은 이전 epoch에
재설치할 수 없지만, 기본 모드로 실행하면 기존 기록을 과거 주장으로 조회할 수
있다.

`recovery_blocked_observation`과 `mqtt_ready_observation`은 DB 조회가 끝난
뒤 각각 현재 런타임의 메모리 상태에서 읽는다. 이 값들은 DB와 원자적으로
동일한 순간의 상태가 아니며 `null`은 알 수 없다는 뜻이다. 차단 여부가
`false`여도 유효한 복구 증명이 있거나 작업 진행이 허용된다는 뜻은 아니다.
MQTT 준비 상태도 장치 연결, 신원이나 실제 위치를 증명하지 않는다.

이 API는 **가상 환경의 진단만** 제공한다. 새로운 명령이나 이벤트 처리,
예약 해제, 재시도, 복구 승인 기능은 없다. 실제 로봇 관제·정지·안전 근거로
사용하지 않는다. 기존 `/simulation`과 같이 로컬 접속과 Bearer 토큰이 필요하고
응답은 `Cache-Control: no-store`다. 런타임이 실행 중이면 MQTT 연결 단절
상태에서도 마지막 DB 기록을 조회할 수 있다. 실행되지 않은 런타임과 구성되지
않았거나 존재하지 않는 작업은 거부한다.

진단 및 기존 작업·대기 이벤트 조회가 SQLite를 기다리는 동안 런타임 전체
잠금은 유지하지 않는다. 종료는 신규 workflow 발행을 먼저 차단하고 통신을
정리한 뒤 이미 시작된 조회가 끝날 때까지 DB 소유권을 보존한다. 다른
프로세스의 SQLite 잠금이 해제되지 않아 조회가 실패할 수 있으며, 이 경우 API는
상세 DB 오류 없이 `503`을 반환한다. 종료 이전에 시작된 조회의 응답은 종료와
경합할 수 있고 메모리 관측은 위에서 설명한 대로 DB 스냅샷과 별개다.

```powershell
$env:TEMP = (Resolve-Path .venv).Path
$env:TMP = $env:TEMP
.\.venv\Scripts\python.exe -m unittest server.tests.test_sim_task_diagnostics -v
```
