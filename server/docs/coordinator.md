# 배정·구간 예약·주문 연결: 격리 시뮬레이션

`server.coordinator.Coordinator(store, map_data, publisher=None, ack_timeout=3)`는
맵 기반 배정 후보와 첫 이동 구간을 계산하고, SQLite의 `AllocationStore`에
작업·로봇·예약·주문을 원자적으로 기록한 뒤 명시적 호출 시 주문을 발행한다.
이 코드는 FastAPI나 MQTT 수신기에 자동 연결되지 않는다.

1. `prepare(task_id, pickup_node, candidates, action_at_end)`는 **기존 PENDING
   작업**에 대해 가용 후보 중 상차 지점까지 최단 거리의 로봇을 고른다.
   `plan_segment`로 다음 대기 지점까지 필요한 노드·공유 엣지·구역을 계산해
   한 트랜잭션으로 배정하며, 전체 경로와 그 구간의 `released_until`을
   설계 문서 주문 형식으로 저장한다. 예약 전에 명시적으로 활성화되고
   연결된 시뮬레이션 발행자의 상태를 확인한다. 발행자가 없거나 연결이
   불가능하면 예약을 만들지 않는다. 예외 발생 시 전송하지 않는다.
2. `publish(task_id)`는 같은 Coordinator 인스턴스가 성공적으로 준비한
   작업만 처리한다. 저장된 payload와 배정 정보를 확인하고, 발행 가능 여부를
   확인한 다음, 같은 트랜잭션에서 작업이 `ASSIGNED`인지, 주문 내용과
   배정·구간 자원이 모두 기대값과 같은지 다시 검사하고 `pending → uncertain`을
   **먼저** DB에 기록한다. 발행 시도 중이거나 브로커가 확인한 주문은 작업
   전이를 차단한다. 안전한 취소·복구 규격이 정해지기 전의 보수적 제한이다.
3. 그 뒤 전용 `OrderPublisher`로 한 번 발행하고, 설정된 시간 이내에
   브로커의 PUBACK을 확인하며 작업·배정·주문·점유를 DB 트랜잭션에서 다시
   검사한 경우에만 `acked`를 기록한다. 송신 오류·타임아웃이나 재검증 실패는
   `uncertain`으로 남고, 어떤 경우에도 자동 재전송하거나 구간 점유를 해제하지
   않는다. PUBACK은 로봇의 수신·실행 증거가 아니며, 발행 후 재검증이 실패해도
   이미 전달된 명령을 되돌리거나 로봇을 정지시키지는 못한다.

새 프로세스 또는 새 Coordinator 인스턴스는 이전의 `pending`을 포함한 모든
주문을 자동 발행하지 않는다. 이전 예약·주문과 로봇 상태의 재동기화 및
운영자 복구 절차는 아직 구현되지 않았다. 발행자는 기본 `None`으로 비활성화되며,
발행 요청은 준비 상태 검사에 실패해도 그 인스턴스에서 다시 시도할 수 없다.
이때 `pending`과 점유는 그대로 남고 별도의 복구가 필요하다.
현재 `OrderPublisher`는 명시적 활성화, `sim-` ID, 재연결이 꺼진 전용
클라이언트가 필요한 **일회성 시뮬레이션용**이다. 한 Coordinator는 발행자
객체를 선점하여 한 작업만 준비하며, 같은 발행자 객체를 다른 Coordinator가
동시에 사용할 수 없다. 준비가 확실히 롤백되고 DB에 배정·주문이 없는 것이
확인된 경우에만 선점을 해제하고 다시 준비할 수 있다. DB 상태를 확인할 수
없으면 선점을 유지한다. 이 보호는 같은 프로세스의 같은 객체에만 적용되며,
다른 MQTT 클라이언트를 막지 못한다. 별도 격리 브로커를 호출자가 제공해야 한다.
`sim-` 접두사나 별도 토픽 자체가 물리적 격리를 보장하지 않는다.

`candidates`는 호출자가 준비한 `RobotCandidate(robot_id, node, available)`
목록이다. 이 코드는 MQTT 과거 관측이나 `state_received_live`를 가용·현재
위치로 자동 추론하지 않는다. 맵 버전·실제 로봇 위치·가용성·안전한 구역과
대기 지점·정지거리·로봇의 후단 이탈은 호출자가 검증해야 한다. 후보가 이미
목적지에 있거나 다음 대기 노드가 없는 경우 등 구간을 만들 수 없으면
배정하지 않는다. 최종 경로 `action_at_end`의 실행 시점 및 형식, 중복 방지,
재연결과 로봇 측 정지 인터록은 팀의 실제 프로토콜이 필요하다.

맵은 입력을 복사해 검증한 뒤 JSON 정규 표현의 SHA-256을 내부 지문으로 사용한다.
같은 `map_id@version`이라도 내용이 다르면 같은 DB에서 새 배정을 거부한다.
이는 팀 맵 갱신 규약이 정해지기 전의 임시 보수적 제한이며 MQTT 필드를
추가하지 않는다. 맵 변경이나 잠금 해제·운영 복구는 지원하지 않는다.

이 연결은 **실물 운행용이 아니다**. 점유 재복구·후단 이탈·실제 상태의
신선도 및 인증이 합의·구현·검증되기 전까지 실물 로봇이나 실물 브로커와
연결하지 않는다. 설계 문서에서 정하지 않은 대기 노드·엣지 점유의
보수적 처리 및 세부 제약은 [구간 계획](segments.md)을 참고한다.

## 별도 로컬 브로커 종단간 테스트

다음 선택적 테스트는 `MOSQUITTO_EXE`에 지정된 Mosquitto 실행 파일로
루프백 전용 임시 브로커를 새로 띄우고, 가짜 `sim-` 로봇의 구독·배정·
예약·QoS 1 주문 수신과 PUBACK, SQLite 재열기, 다른 로봇의 점유 충돌을
확인한다. 기존 브로커나 `.env`를 사용하지 않고 종료 시 자신이 띄운
프로세스와 임시 파일을 정리한다. `MOSQUITTO_EXE`가 설정되지 않으면
해당 테스트는 건너뛴다.

```powershell
$env:MOSQUITTO_EXE = '<mosquitto.exe의 절대 경로>'
.\.venv\Scripts\python -m unittest discover -s server/tests -p test_fleet_mqtt_integration.py -v
Remove-Item Env:MOSQUITTO_EXE
```

이 시험은 가짜 로봇·임시 맵·로컬 브로커만 사용한다. 실물에 대한 위치
확인, 충돌 방지 또는 안전 정지 검증을 대신하지 않는다.
