# 다음 구간 주문 발행: 격리 시뮬레이션 전용

`ProgressPublisher`는 `SegmentProgress.advance`가 DB에 준비한 2번째 이후
`pending` 주문을 별도의 `OrderPublisher`로 명시적으로 한 번 발행한다. 새
MQTT 토픽이나 주문 필드는 추가하지 않는다. 이 기능은 FastAPI나 MQTT 이벤트
수신에 자동으로 연결되지 않고 기본 발행자가 없어 비활성화된다.

1. 동일 DB의 `RecoveryGate`를 새 프로세스에서 초기화하고, 현재 가상 로봇의
   세션·이전 순번·정지 지점에 대한 일회용 challenge 응답을 검증한다.
2. 다음 pending 주문, 저장된 배정과 맵 기반 구간 자원을 읽고 전용 발행자를
   선점한다. gate의 `serialized()` 범위에서 발행 가능 여부를 확인하고
   `SegmentProgress.mark_attempted`의 SQLite 트랜잭션으로 주문·점유·맵·이전
   순번 증명을 다시 검증해 `pending → uncertain`을 먼저 기록한다.
3. 같은 gate 락을 유지하고 별도 SQLite writer 트랜잭션에서 `uncertain`
   주문·점유·맵·증명을 다시 확인한다. 그 writer 락을 유지한 채 QoS 1,
   retain 없는 주문을 전용 Paho 클라이언트 큐에 넣는다. 다른 gate 인스턴스의
   epoch 변경과 DB 점유 변경이 그 사이에 끼어들 수 없도록 하는 제한이다.
   락을 놓고 정해진 시간 동안 PUBACK을 기다린 뒤에만,
   `mark_broker_acked`로 주문·점유·복구 증명을 다시 검사해 `acked`로 바꾼다.

오류·응답 지연·종료 시 주문이 실제 전달됐는지는 확정하지 않으며, 시도
기록이 이미 남았다면 `uncertain`과 구간 점유를 유지한다. 재시작 후 자동
재전송하지 않고 새로운 challenge와 명시적인 호출이 필요하다. PUBACK은
브로커 수신 확인이지 로봇 수신이나 실행의 증거가 아니다.

발행 객체를 선점한 뒤 생긴 모든 실패는 보수적으로 회복 증명을 무효화하고
해당 발행 객체와 클라이언트를 다시 쓰지 않는다. DB에 무효화를 기록하는
도중 오류가 나더라도 현재 gate 인스턴스의 로컬 증명은 차단되며 오류가
호출자에게 전달된다. 재시도하려면 새로운 전용 클라이언트와 유효한 새
challenge가 필요하다. `None` 등으로 발행이 꺼진 경우에는 선점 자체를
하지 않는다.

설계 v0.2는 후단 이탈 인증, 재부팅 상태 동기화, 안전 정지 및 주문 중복
규약의 상세를 정하지 않았다. 현재 구현은 인증과 물리적 안전을 보장하지
않으며 `sim-` ID 및 별도 격리 브로커를 사용하는 가상 시험 전용이다.
gate 락은 같은 프로세스가 **관측한** 단절 처리와 큐 등록의 순서만 정하며,
아직 감지하지 못한 물리 단절, 원시 Paho 접근이나 다른 프로세스의 외부
기기 제어를 막지 못한다. SQLite 거래와 네트워크 전송은 원자적이지 않으므로
큐에 넣은 뒤 DB 거래가 실패해도 결과는 불확실한 상태로 남는다. 실물 브로커와
로봇에 이 기능을 연결하면 안 된다.
