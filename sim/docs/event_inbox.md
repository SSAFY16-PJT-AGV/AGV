# Simulation event inbox proposal

This is an internal SQLite inbox, not a change to the MQTT protocol or its event fields. It accepts only explicitly enabled simulated robots and a fixed robot-to-task mapping. It stores canonical validated rear-clear events before they can be acknowledged at the transport layer. Identical `(robot_id,event_id)` and content is idempotent; different content under the same ID is a conflict.

`store(robot_id, payload)` commits a pending record before returning. `retry(robot_id, event_id, progress)` explicitly replays the stored content through the existing gated `SegmentProgress.advance`; only `advanced`, `duplicate`, or `finished` results become applied. Invalid session, outdated proof, reservation conflict, and SQLite errors leave the event pending. No automatic retry or deletion is performed. A failure after progress commits but before the inbox marks it applied can be retried when the original proof is valid; the progress event journal prevents repeating its effects. Even after restart and loss of the old proof, a retry can reconcile a matching committed progress journal and validated order history in a single database transaction; this only changes the inbox bookkeeping to applied and never moves a robot or releases resources. If journal, allocation, map fingerprint, or order history disagree, reconciliation fails closed and leaves the event pending.

Retries in one process are serialized per database; separate processes can call advance concurrently, but the progress transaction and event journal enforce idempotency. The inbox does not itself authenticate senders, prove a physical rear clearance, authorize driving, or replace the recovery gate. It must not be attached to a real robot. MQTT delivery durability also depends on manual acknowledgment after store, broker session/persistence settings, and explicit retry handling; this module alone provides no transport guarantees.

`list_pending()` returns allowed robots’ still-pending event IDs and payloads for explicit recovery after restarting the process. It never retries them automatically. Applied events and their results remain recorded; `rejected` is reserved for a future explicit reconciliation workflow.
